Gradle Setup

Gradle does not require a formal installer. It consists of a single, zip download that includes everything you need.

The Gradle home page is http://gradle.org. The download link is https://gradle.org/install/. There are three distributions available:

  • Complete: binaries, source code, and offline docs

  • Binary only

  • Source code only

Either the complete or binary distributions will do, but it’s usually worth it to get the complete distribution. Online docs are available, but the complete distribution includes a large number of samples that can be very useful.

To install Gradle:

  • Install the Java Standard Edition JDK. As of Gradle 5, Java version 1.8 or higher is required

  • Download and unzip the Gradle distribution

  • Assign a GRADLE_HOME environment variable to the unzipped folder

  • Add %GRADLE_HOME%\bin (Windows) or $GRADLE_HOME/bin to your PATH

Verify the installation by opening a command prompt and typing:

> gradle -v

The output should show the Gradle version the Java version, the (included) Groovy version, and other operating system information.

You don’t need to install Groovy to use Gradle.

Gradle includes a Groovy distribution, which is used to drive Gradle. If you create a Groovy project (discussed in another section), you can specify any Groovy distribution you wish, but running the build can be done without one.

Be sure to bookmark the User Guide, either online at https://docs.gradle.org/current/userguide/userguide.html or included in your distribution.

The Gradle DSL can be either Groovy-based or Kotlin-based. As the Groovy version is much more mature than the Kotlin version, the rest of this course will focus on using the Groovy-based DSL.

Just Enough Groovy to Get By

This section reviews the basics of the Groovy programming language. The Gradle build files consist largely of a Domain Specific Language, written in Groovy, for builds. In addition to the DSL, any legal Groovy code can be added to the build.

Groovy is a general purpose programming language, based on Java, that compiles to Java byte codes. While it has functional capabilities, it is an object-oriented language that is arguably the next-generation language in the path from C++ to Java.

Basic Syntax

The "Hello, World!" program for Groovy is the one-liner shown in Hello, World! in Groovy.

Example 1. Hello, World! in Groovy
println 'Hello, World!'

Items of note:

  • Semicolons are optional. If you add them, they work, but they’re not required.

  • Parentheses are optional until they’re not. If the compiler guesses correctly where they should have gone, everything works. Otherwise, add them back in. The println method takes a String argument. Here the parentheses are left out.

  • There are two types of strings in Groovy: single-quoted strings, like 'Hello', are instances of java.lang.String. Double-quoted strings are Groovy strings and allow interpolation, shown below.

There are no "primitives" in Groovy. All variables use the wrapper classes, like java.lang.Integer, java.lang.Character, and java.lang.Double. The native data type for integer literals, like 3, is Integer. The native data type for floating point literals, like 3.5, is java.math.BigDecimal.

Example 2. Some basic data types in Groovy
assert 3.class == Integer
assert (3.5).class == BigDecimal
assert 'abc' instanceof String  (1)
assert "abc" instanceof String  (2)

String name = 'Dolly'
assert "Hello, ${name}!" == 'Hello, Dolly!' (3)
assert "Hello, $name!" == 'Hello, Dolly!'   (4)
assert "Hello, $name!" instanceof GString
1 Single-quoted strings are Java strings
2 Double-quoted strings are also Java strings unless you interpolate
3 String interpolation, full form
4 String interpolation, short form when there is no ambiguity

Note that you can invoke methods on literals, because they are instances of the wrapper classes.

Groovy lets you declare variables with either an actual type, like String, Date, or Employee, or you can use def. See Static vs Dynamic data types.

Example 3. Static vs Dynamic data types
Integer n = 3
Date now = new Date()

def x = 3
assert x.class == Integer
x = 'abc'
assert x.class == String
x = new Date()
assert x.class == Date

Java imports the java.lang package automatically. In Groovy, the following packages are all automatically imported:

  • java.lang

  • java.util

  • java.io

  • java.net

  • groovy.lang

  • groovy.util

The classes java.math.BigInteger and java.math.BigDecimal are also available without an import statement.

The assert method and the Groovy Truth

The assert method in Groovy evaluates its argument according to the "Groovy Truth". That means:

  • Non-zero numbers (positive and negative) are true

  • Non-empty collections, including strings, are true

  • Non-null references are true

  • Boolean true is true.

The Groovy Truth is illustrated in The Groovy Truth.

Example 4. The Groovy Truth
assert 3;     assert -1;  assert !0
assert 'abc'; assert !''; assert !""

assert [3, 1, 4, 1, 5, 9]
assert ![]

Asserts that pass return nothing. Asserts that fail throw an exception, as in Failing assertions, with lots of debugging information included.

Example 5. Failing assertions

assert 12 == x + y  // passes

assert 12 == 3 * x + 4.5 * y / (2/x + y**3)  // fails

Operator Overloading

In Groovy, every operator corresponds to a method call. For example, the + sign invokes the plus method on Number. This is used extensively in the Groovy libraries. Some examples are shown in Operator overloading.

Example 7. Operator overloading
assert 3 + 4 == 3.plus(4)
assert 3 * 4 == 3.multiply(4)

assert 2**6 == 64
assert 2**6 == 2.power(6)

assert 'abc' * 3 == 'abcabcabc' // String.multiply(Number)
try {
    3 * 'abc'
} catch (MissingMethodException e) {
    // no Number.multiply(String) method
}

String s = 'this is a string'
assert s + ' and more' == 'this is a string and more'
assert s - 'is' == 'th is a string'
assert s - 'is' - 'is' == 'th  a string'

Date now = new Date()
Date tomorrow = now + 1 // Date.plus(Integer)
assert tomorrow - 1 == now  // Date.minus(Integer)

Groovy has an exponentiation operator, **, as shown.

In Java, the == operator checks that two references are assigned to the same object. In Groovy, == invokes the equals method, so it checks for equivalence rather than equality. If you want to check references, use the is method.

Collections

Groovy has native syntax for collections. Use square brackets and separate values by commas to create an ArrayList. You can use the as operator to convert one collection type to another. Collections also have operator overloading, implementing methods like plus, minus, and multiply.

Example 8. Collection examples and methods
def nums = [3, 1, 4, 1, 5, 9, 2, 6, 5]
assert nums instanceof ArrayList

Set uniques = nums as Set
assert uniques == [3, 1, 4, 5, 9, 2, 6] as Set

def sorted = nums as SortedSet
assert sorted == [1, 2, 3, 4, 5, 6, 9] as SortedSet
assert sorted instanceof TreeSet

assert nums[0] == 3
assert nums[1] == 1
assert nums[-1] == 5 // end of list
assert nums[-2] == 6

assert nums[0..3] == [3, 1, 4, 1]  // two dots is a Range
assert nums[-3..-1] == [2, 6, 5]
assert nums[-1..-3] == [5, 6, 2]

String hello = 'hello'
assert 'olleh' == hello[-1..0]  // Strings are collections too

A Range in Groovy consists of two values separated by a pair of dots, as in from..to. The range expands starting at the from position, invoking next on each element until it reaches the to position, inclusive.

Maps use a colon notation to separate the keys from the values. The square bracket operator on a map is the getAt or putAt method, depending on whether you are accessing or adding a value. The dot operator is overloaded similarly. See Map instances and methods for details.

Example 9. Map instances and methods
def map = [a:1, b:2, c:2]
assert map.getClass() == LinkedHashMap
assert map.a == 1         (1)
assert map['b'] == 2      (2)
assert map.get('c') == 2  (3)

2 Uses putAt method
3 Java still works, too

Closures

Groovy has a class called Closure that represents a block of code that can be used like an object. Think of it as the body of an anonymous method, which is an oversimplification but not a bad start.

A closure is like a Java 8 lambda, in that it takes arguments and evaluates a block of code. Groovy closures can modify variables defined outside them, however, and Java 8 does not have a class called Lambda.

Many methods in Groovy take closures as arguments. For example, the each method on collections supplies each element to a closure, which is evaluated with it. An example is in Using Groovy’s each method with a closure argument.

Example 10. Using Groovy’s each method with a closure argument
def nums = [3, 1, 4, 1, 5, 9]

def doubles = []      (1)
nums.each { n ->      (2)
    doubles << n * 2  (3)
}

assert doubles == [6, 2, 8, 2, 10, 18]
1 Empty list
2 each takes a closure of one argument, before the arrow, here called n
3 Left-shift operator appends to a collection

Modifying a variable defined outside a closure is considered a side-effect, and not good practice. The collect method, discussed later, is preferred.

This is a natural way to double the values in a list, but there is a better alternative, called collect. The collect method transforms a collection into a new one by applying a closure to each element. It is similar to the map method from Java 8, or just think of it as the map operation in a map-filter-reduce process.

Example 11. Using Groovy’s collect method to transform a collection
def nums = [3, 1, 4, 1, 5, 9]
def doubles == nums.collect { it * 2 }
assert doubles == [6, 2, 8, 2, 10, 18]

When a closure has a single argument (which is the default), and you don’t give that argument a name using the arrow operator, the dummy name defaults to the word it. In this case, the collect method creates the doubles collection by applying it * 2 in a closure to each element.

If a method takes a closure as its last argument, you can put it after the parentheses. This is sufficiently common that it should be emphasized.

Standard Groovy Idiom

If a Groovy method takes a Closure as its last argument, the closure is normally added after the parentheses.

For example, the java.lang.Number class in the Groovy JDK has a method called downto which takes two arguments, a Number and a Closure. The method decrements from the given number down to the first argument, supplying each value to the second argument. Three different ways of invoking the method are shown in Closure as the last argument to a method.

Example 12. Closure as the last argument to a method
10.downto(7) { println it }   // Standard Groovy idiom
10.downto(7, { println it })  // Java developer coding in Groovy
10.downto 7, { println it }   // Legal, but can be confusing

Each of these will print the numbers 10, 9, 8, 7, each on a single line.

POGOs

Java classes with just attributes and getters and setters are often called Plain Old Java Objects, or POJOs. Groovy has similar classes called POGOs. An example is in A simple POGO.

Example 13. A simple POGO
import groovy.transform.Canonical
@Canonical
class Event {
    String name
    Date when
    int priority
}

This little class actually has a lot of power. For a POGO:

  • The class is public by default

  • Attributes are private by default

  • Methods are public by default

  • Getter and setter methods are generated for each attribute not marked public or private

  • Both a default constructor and a "map-based" constructor (uses arguments of the form "attribute:value") are provided

In addition, this POGO include the @Canonical annotation, which triggers an Abstract Syntax Tree (AST) transformation. AST transformations modify the syntax tree created by the compiler during the compilation process in specific ways.

The @Canonical annotation is actually a short-cut for three other AST transformations: @ToString, @EqualsAndHashCode, and @TupleConstructor. Each does what they sound like, so in this case, the @Canonical annotation adds to this class:

  • A toString override that displays the fully-qualified name of the class, followed by the values of the attributes, in order from top down

  • An equals override that does a null-safe check for equivalence on each attribute

  • A hashCode override that generates an integer based on the values of the attributes in a fashion similar to that laid out by Joshn Bloch in his Effective Java book long ago

  • An additional constructor, that takes the attributes as arguments, in order

That’s a lot of productivity for seven lines of code. Using the Event POGO shows how to use it.

Example 14. Using the Event POGO
Event e1 = new Event(name: 'Android Studio 1.0',
    when: Date.parse('MMM dd, yyyy', 'Dec 8, 2014'),
    priority: 1)

Event e2 = new Event(name: 'Android Studio 1.0',
    when: Date.parse('MMM dd, yyyy', 'Dec 8, 2014'),
    priority: 1)

assert e1.toString() ==
    'Event(Android Studio 1.0, Mon Dec 08 00:00:00 EST 2014, 1)'
assert e1 == e2

Set events = [e1, e2]
assert events.size() == 1

The Gradle Wrapper

The Gradle wrapper is a task that generates a build script that can be used by clients who do not yet have Gradle installed. The task generates both a Windows and a Unix script, plus a minimal jar distribution.

The wrapper task is built into Gradle. It will generate build scripts based on the currently installed version of Gradle.

> gradle wrapper

This will generate the scripts gradlew and gradlew.bat it the project directory, and a folder called gradle\wrapper which contains gradle-wrapper.jar and gradle-wrapper.properties.

The gradlew script is for Unix environments, and the gradlew.bat file is for Windows.

Executing a script is as simple as:

> ./gradlew <task>    // Unix
> gradlew.bat <task>  // Windows

(Note you don’t need the .bat extension on the command line, but it works.)

Either command will download a binary Gradle distribution and store it in a user’s home directory, under .gradle/wrapper/dists.

Specifying Gradle wrapper versions

You can specify which version of Gradle to use in the wrapper either on the command line, or using a Gradle task.

On the command line, the flag --gradle-version <version> does the job.

> gradle wrapper --gradle-version 7.6

That command generates a wrapper for Gradle version 7.6.

Alternatively, you can specify the Gradle version in a wrapper task.

task wrapper(type: Wrapper) {
    gradleVersion ='7.6'
}

The generated files should be checked into source control, as this provides a reliable way of specifying which version of Gradle works for the current project.

While using a Gradle wrapper task is an easy way to specify the version, it’s not necessary to have that task in the build file to generate the wrapper. If you still want to change the wrapper version and a wrapper has already been generated, you can do so by simply editing the gradle/wrapper/gradle-wrapper.properties file.

Inside the gradle-wrapper.properties file, the distributionUrl property specifies the Gradle version. Updating that property is sufficient to revise the wrapper.

Task Shortcuts

You can execute multiple tasks by separating them by spaces.

> gradle tasks dependencies properties

This will run the tasks, dependencies, and properties tasks consecutively.

Task names can be abbreviated. You only have to give enough letters to make the task unique.

For example, this will run the dependencies task.

> gradle dep

In fact, simply gradle d is enough to be unique in this instance. Where there is a conflict, Gradle will tell you.

> gradle pro
FAILURE: Build failed with an exception.

* What went wrong:
Task 'pro' is ambiguous in root project 'minimal_java_project'. Candidates are: 'projects', 'properties'.

BUILD FAILED

In this case, pro could have been either projects or properties. One more letter will resolve the ambiguity.

You can also use the camel-case initial caps as an abbreviation. The standard Java project includes tasks called buildDependencies and processTestResources.

> gradle bD  // runs buildDependencies
> gradle pTC // runs processTestResources

Either is a great simplification.

In a multi-project build, the projects task shows the names of the subprojects and any given documentation.

Build Lifecycle

Gradle builds run through three distinct phases:

Initialization

Read environment configuration files init.gradle and gradle.properties, and set up all subprojects listed in settings.gradle. This is relevant when doing multi-project builds.

Configuration

Evaluate all build scripts and build the model, including the directed acyclic graph (DAG)

Execution

Execute the desired tasks

The configuration phase is when Gradle reads all the task declarations and sets any required properties.

Note that the group and description properties were set for the printProperties task during the configuration phase. In general, you want to configure tasks rather than write execution code, as this favors a "what to do" approach rather than "how to do it". The section on writing custom tasks goes into much more detail.

Ad Hoc Tasks

The Gradle DSL is extensive, and often you won’t need anything beyond what the plugins provide. Sooner or later, however, every build becomes a custom build, and Gradle was designed with that in mind.

This section discusses how to create your own tasks for Gradle builds.

Use the task keyword to define a task, as in Ad hoc task to say hello.

Example 17. Ad hoc task to say hello
task hello {
    doLast {
        println 'hello'
    }
}

The doLast block identifies the code to be run during the execution phase. Anything outside that block is executed as part of the configuration phase.

Task Dependencies

Gradle tasks can depend upon one another. Here the intro task depends on the hello task.

task hello {
    doLast {
        println 'hello'
    }
}

task intro(dependsOn: hello) {
    doLast {
        println 'introduction'
    }
}

Executing the intro task runs both.

> gradle intro
:hello
hello
:intro
introduction

As an alternative syntax, you can specify dependsOn as a task property.

task hello {
    doLast {
        println 'hello'
    }
}

task intro {
    dependsOn hello
    doLast {
        println 'introduction'
    }
}

Use whichever syntax is more intuitive for you. They both do the same thing.

As with almost everything in Gradle, you can use a dot notation instead of a block if you prefer.

task hello {
    doLast {
        println 'hello'
    }
}

task intro {
    doLast {
        println 'introduction'
    }
}

intro.dependsOn hello

Directed Acyclic Graph

During the configuration phase, all the tasks are assembled into a directed acyclic graph (DAG). This means there can be no loops in the task graph.

The DAG is available inside the build file through the gradle.taskGraph. Here is a typical usage, from the User Guide:

Example 18. Using the DAG
task distribution {
    doLast {
        println "We build the zip with version=$version"
    }
}

task release(dependsOn: 'distribution') {
    doLast {
        println 'We release now'
    }
}

gradle.taskGraph.whenReady {taskGraph ->
    if (taskGraph.hasTask(release)) {
        version = '1.0'
    } else {
        version = '1.0-SNAPSHOT'
    }
}

The distribution and release tasks now set different versions.

> gradle distribution
:distribution
We build the zip with version=1.0-SNAPSHOT

> gradle release
:distribution
We build the zip with version=1.0
:release
We release now

If there is no obvious dependency between tasks but you still need ordering, try the mustRunAfter and shouldRunAfter properties.

task hello {
    doLast {
        println 'hello'
    }
}

task intro {
    doLast {
        println 'introduction'
    }
}

intro.mustRunAfter hello

The intro task will not run until the hello task is executed.

> gradle intro hello
:hello
hello
:intro
introduction

The shouldRunAfter method works the same way but is not as strict (for example, it is ignored in parallel builds). Use it when the dependency is not absolutely required. The assumption is that the tasks are truly independent, but if both are run together there is a preferred ordering.

Finally, you can use finalizedBy to make one task run after another.

task hello {
    doLast {
        println 'hello'
    }
}

task intro {
    doLast {
        println 'introduction'
    }
}

intro.finalizedBy hello

Now whenever you run gradle intro, the hello task will run after the intro task completes.

Task Types

The Gradle API has many built-in tasks available, which can be customized.

Copy

For example, Configuring the Copy task configures the Copy task.

Example 19. Configuring the Copy task
def copyOutputs(type: Copy) {
    from "$buildDir/libs"
    into '../results'
}

The buildDir property of Project defaults to the build subdirectory of the default projectDir, which defaults to the root of the project. In a Java project, the build produces a jar file that is placed in the libs folder under build. This task copies it from there to a results folder in the parent.

The task configures an instance of the built-in task type Copy, which is generally much easier than writing a copy task by hand. This fits in with the Gradle goal of configuration rather than execution, or specifying what to do rather than how to do it.

The Copy type specifies from and into methods at configuration time, as shown. You can customize the so-called "copy spec" (the group of files to be copied) using include or exclude, whose syntax support Ant-style patterns. There are also methods like filter and rename.

Here is a more elaborate copy task, from the User Guide.

task copyTaskWithPatterns(type: Copy) {
    from 'src/main/webapp'
    into 'build/explodedWar'
    include '**/*.html'
    include '**/*.jsp'
    exclude { details -> details.file.name.endsWith('.html') &&
                         details.file.text.contains('staging') }
}

This task will copy all the HTML and JSP files from the src/main/webapp folder into the build/explodedWar folder, leaving out any HTML files whose text contains the word "staging".

Sync

The Sync type is similar to the Copy type, but it removes any files from the destination directory that were not specified.

task libs(type: Sync) {
    from configurations.runtime
    into "$buildDir/libs"
}

This task will copy the jar files in the runtime configuration into the libs folder under the build directory, and will remove any files in the destination folder that are not part of that set.

You can keep the Sync task from removing all the files in the destination directory by using the preserve method, as shown in this example from the DSL reference.

task sync(type: Sync) {
    from 'source'
    into 'dest'
    preserve {
        include 'extraDir/**'
        include 'dir1/**'
        exclude 'dir1/extra.txt'
    }
}

Rather than deleting all the files in the dest directory before the copy, this task avoids deleing all the files in the extraDir tree and the dir1 tree, except for the file extra.txt.

Archive Types

Task types Zip, Tar, Jar, War, and Ear are all available.

The User Guide contains an example of how to use the Zip type.

apply plugin: 'java'

task zip(type: Zip) {
    from 'src/dist'
    into('libs') {
        from configurations.runtime
    }
}

The default name of the generated zip file is determined by the "base" plugin, which you can include yourself but is often included by others (like the "java" plugin). The generated archive name is:

[archiveBaseName]-[archiveAppendix]-[archiveVersion]-[archiveClassifier].[archiveExtension]

where the default values are:

  1. archiveBaseName: project name

  2. archiveAppendix: empty string

  3. archiveVersion: project version

  4. archiveClassifier: empty string

  5. archiveExtension: zip for Zip, tar for Tar, etc.

The default location of the generated archive is in "$buildDir/distributions". Actually, jars and wars go into "$buildDir/libs", while zips and tars go into the distributions directory.

There is no "unzip" task. Instead, you use a Copy task type and wrap a zipTree or tarTree around the archive name.

This sample from the User Manual shows how it’s done:

task unpackFiles(type: Copy) {
    from zipTree("src/resources/thirdPartyResources.zip")
    into "$buildDir/resources"
}

Note the zipTree works for jars, wars, and ears.

Files

The Project class has a method called files that is used to create a file collection. The method evaluates its argument relative to the project directory.

// Using a relative path
File configFile = file('src/config.xml')

// Using an absolute path
configFile = file(configFile.absolutePath)

// Using a File object with a relative path
configFile = file(new File('src/config.xml'))

The returned value is an instance of FileCollection, which has the normal Groovy enhancements. You can add collections using the plus operator, or subtract one collection from another using minus.

FileCollection collection = files('src/file1.txt',
                                  new File('src/file2.txt'),
                                  ['src/file3.txt', 'src/file4.txt'])

// Iterate over the files in the collection
collection.each { File file ->
    println file.name
}

// Convert the collection to various types
Set set = collection.files
Set set2 = collection as Set
List list = collection as List
String path = collection.asPath
File file = collection.singleFile
File file2 = collection as File

// Add and subtract collections
def union = collection + files('src/file3.txt')
def different = collection - files('src/file3.txt')

Deleting files and folders is done using the Delete task, or the delete method on Project.

Custom Tasks

Ad hoc tasks aren’t easily reusable. Instead, you can write your own class that represents a task type.

The goal is to implement the Task interface, which is most easily done by extending the DefaultTask class.

class Greeting extends DefaultTask {
    String user = 'World'

    @TaskAction
    void sayHello() {
        println "Hello, $user!"
    }
}

The Greeting task extends DefaultTask and adds a method annotated with @TaskAction. That method (sayHello in this case) becomes the operation executed at run time when a task of that type is run.

You use the custom task by creating one or more tasks of that type, optionally supplying values for the properties at configuration time.

If the Greeting class is added directly to build.gradle, you can define tasks of that type in the same file:

task hi(type: Greeting)

task whatUp(type: Greeting) {
    user = 'Dolly'
}

class Greeting extends DefaultTask {
    String user = 'World'

    @TaskAction
    void sayHello() {
        println "Hello, $user!"
    }
}

If the user invokes the hi task (using gradle hi), the build will print "Hello, World!" to the console. If you user runs gradle whatUp, the result will print "Hello, Dolly!" instead.

It is not unusual to add your custom tasks directly to the build file like this, because the build file already knows both the Groovy API and the Gradle API. The resulting class is only available in the current build, however. The next step would be to move it to its own source tree, under $projectDir/src/main/groovy in package structure, which can then have its own build dependencies as well. Ultimately you may decide to add the class to a completely separate project, especially if you plan to create a plugin.

More details about this process are discussed in the plugins section below.

Configuring Repositories

The repositories block tells Gradle where to find the dependencies. By default, Gradle uses either jcenter() or mavenCentral(), which represent the default Bintray JCenter repository and the public Maven Central Repository, respectively.

Example 20. The default JCenter repository
repositories {
    jcenter()
}

This refers to the JCenter repository located at https://jcenter.bintray.com. Note that it uses HTTPS for the connection.

There are two shortcuts available for Maven repositories. The mavenCentral() syntax refers to the central Maven 2 repository at http://repo1.maven.org/maven2. The mavenLocal() syntax refers to your local Maven cache.

Example 21. Built-in Maven repositories in the repositories block
repositories {
    mavenLocal()    (1)
    mavenCentral()  (2)
}
1 Local Maven cache
2 Public Maven Central repository

Any Maven repository can be added to the default list using a maven argument with a url block.

Example 22. Adding a Maven repo from a URL
repositories {
    maven {
        url 'http://repo.spring.io/milestone'
    }
}

Password protected repositories use a credentials block, as Accessing a Maven repo requiring credentials taken from the Gradle user guide shows.

Example 23. Accessing a Maven repo requiring credentials
repositories {
    maven {
        credentials {
            username 'username'
            password 'password'
        }
        url 'http://repo.mycompany.com/maven2'

Inside a typical build.gradle file involving a programming language (like Java, Groovy, or Kotlin), there is a block called dependencies that lists which libraries your project uses. Configurations

Gradle dependencies are grouped into configurations, which are simply named bundles of dependencies. The Java Library plugin (which includes the Java plugin) defines a set of configurations, which include:

implementation

Dependencies required to compile the project

api

Like implementation, but also exposed to client projects

runtimeOnly

Dependencies needed during execution, like JDBC drivers

testImplementation

Dependencies used to compile tests, like JUnit or TestNG

testRuntimeOnly

Dependencies needed during the execution of tests, like a JDBC driver for a test database

The older Java plugin defined the configurations compile, runtime, testCompile, and testRuntime. The newer mechanism gives finer grained control over when projects need to be rebuilt when dependencies change. The older configurations are still available, but deprecated.

Various plugins add additional configurations, or you can define your own.

Basic Syntax

Gradle supports several different ways of listing dependencies. The most common is to use quotes with colon-separated group, name, and version values.

In Groovy, both single quotes and double quotes can be used to delimit strings. Double quotes allow interpolation, or variable substitution, but are otherwise identical.

The full syntax for a dependency calls out the group, name, and version numbers explicitly.

Example 27. Full syntax for dependencies
testImplementation group: 'junit', name: 'junit', version: '4.12'

The result of Full syntax for dependencies is entirely equivalent to that in Shortcut syntax for dependencies.

Example 28. Shortcut syntax for dependencies
testImplementation 'junit:junit:4.12'

This is the shortcut form used in the default build file.

It is legal, though not recommended, to specify a version number with a plus sign.

Example 29. Version number as a variable (not recommended)
testImplementation 'junit:junit:4.+'

This tells Gradle that any version of JUnit greater than or equal to 4.0 is required to compile the project’s tests. While this works, it makes the build less deterministic and therefore less reproducible. Explicit version numbers also protect you from changes in later versions of a particular API.

Favor explicit version numbers for dependencies. This protects you from later changes in dependent libraries and makes your build reproducible.

If you want to add a set of files to a configuration without adding them to a repository, you can use the files or fileTree syntax inside the dependencies block.

Example 30. File and directory dependencies
dependencies {
    implementation files('libs/a.jar', 'libs/b.jar')
    implementation fileTree(dir: 'libs', include: '*.jar')
}

The last line uses the same syntax as that employed in the default Gradle build file.

Next, Gradle needs to know where to search to resolve dependencies. This is done through a repositories block.

Managing transitive dependencies manually sounds like a good idea until you actually try to do it. The complexity grows quickly and doesn’t scale well. Gradle is actually very good at resolving versioning issues among dependencies.

Still, Gradle does provide a syntax for including and excluding individual libraries.

Gradle follows transitive dependencies by default. If you want to turn that off for a particular library, use the transitive flag.

2 Full version

Conditional Execution

The Java and Groovy plugins automatically skip tasks that are up to date. This is done based on hash values of the so-called inputs and outputs for those tasks. You can take advantage of that capability in your own builds.

Inputs and Outputs

Every task has a property called inputs and a property called outputs. The former is of type TaskInputs and the latter is of type TaskOutputs. Each of those has properties file, files, and dir.

Before a task is executed, Gradle takes a snapshot of the the inputs and creates a hash of their contents. If the task completes successful, Gradle does the same with the outputs.

Each time after that, Gradle compares the hash of the inputs and outputs. If they are the same, the task is skipped.

Consider a transformation task that parses a file and writes the results to a new directory.

task transform {
    ext.srcFile = file('mydata.csv')
    ext.destDir = new File(buildDir, 'generated')
    doLast {
        println 'parsing the input file...'
        println 'writing output to the build directory...'
    }
}

(An actual implementation would do the parsing and writing, rather than just say it’s doing it.)

Executing gradle transform over and over again would do the work each time, even if nothing has changed.

If the inputs and outputs properties are set, however, this changes.

task transform {
    ext.srcFile = file('mydata.csv')
    ext.destDir = new File(buildDir, 'generated')
    inputs.file srcFile
    outputs.dir destDir
    doLast {
        println 'parsing the input file...'
        println 'writing output to the build directory...'
    }
}

Now running the transform task multiple times executes only the first time, and after that it’s skipped.

> gradle transform
:transform
parsing the input file...
writing output to the build directory...

> gradle transform
:transform UP-TO-DATE

If you write your own custom task, you can use the annotations @InputFile, @OutputDirectory (and a few others) to declare the input and output properties. The mechanism used in this section is necessary when you don’t control the source code of the task.

onlyIf

You can also skip a task by using the onlyIf method. The method takes a closure, and the task only executes if the closure returns true.

From the User Guide:

task hello {
    doLast {
        println 'hello world'
    }
}

hello.onlyIf { !project.hasProperty('skipHello') }

Executing the task without a skipHello property prints hello world.

> gradle hello
:hello
hello world

> gradle hello -PskipHello
:hello SKIPPED

Finally, each task also has an enabled property. Setting it to false disables the task.

The Gradle Daemon and Other Properties

Gradle runs on the JVM and uses additional initialization libraries. This can slow down a build. The Gradle daemon is a long-lived process that caches the required dependencies in memory. It is enabled by default.

Enabling and Disabling the daemon

Starting in version 3.0 (ancient by today’s Gradle standards), the daemon is enabled by default. You can control whether or not to use the daemon on an individual build using the command line flags --daemon and --no-daemon. If a daemon is not running, using --daemon at the command line (or doing any build) will automatically start it.

You can stop the daemon with the --no-daemon flag, which may be necessary to completely reinitialize your build.

You can also stop the daemon by using the --stop command, but that will kill all daemon processes using that version of Gradle.

You can check the status of the Gradle daemon using the --status flag. A typical output is:

> gradle --status
   PID STATUS   INFO
 59066 IDLE     5.4.1

Only daemons for the current Gradle version are displayed. The jps command comes with Java and can be used to identify all Java processes, including Gradle daemons.

> jps
54020 Jps
53494
52888 GradleDaemon

This shows that the Gradle daemon is running with an lvmid of 52888, which is usually, but not always, the process id.

See also https://docs.gradle.org/current/userguide/gradle_daemon.html in the User Guide for more information.

Other Gradle Properties

The gradle.properties file supports additional settings, which can be useful for tuning a build. Note you can also have a gradle.properties file in the project root, which will be used for that project only.

Available properties include:

org.gradle.java.home

Specifies the Java home for the build process, normally set to a JDK

org.gradle.jvmargs

Specifies the JVM args used for the daemon process, like min and max memory

org.gradle.configureondemand

Tells Gradle to attempt to build only subprojects that are needed (incubating)

org.gradle.parallel

Tells Gradle to run in parallel mode (incubating)

It’s very common to set HTTP and HTTPS proxy setting in gradle.properties. Typical values (from the User Manual) are given by:

systemProp.http.proxyHost=www.somehost.org
systemProp.http.proxyPort=8080
systemProp.http.proxyUser=userid
systemProp.http.proxyPassword=password
systemProp.http.nonProxyHosts=*.nonproxyrepos.com|localhost

systemProp.https.proxyHost=www.somehost.org
systemProp.https.proxyPort=8080
systemProp.https.proxyUser=userid
systemProp.https.proxyPassword=password
systemProp.https.nonProxyHosts=*.nonproxyrepos.com|localhost

See the section on working through a proxy in the User Manual for details.

Logging

There are six log levels available by default in a Gradle build file:

  1. error

  2. quiet

  3. warning

  4. lifecycle

  5. info

  6. debug

The default log level is lifecycle.

Set the log level on the command line using a flag.

  • Use -q or --quiet for QUIET and higher

  • Use -i or --info for INFO and higher

  • Use -d or --debug for DEBUG or higher (all messages — very verbose)

If you need to see stacktraces due to some kind of error, the -s or --stacktrace flag will show a truncated version. This is recommended in the documentation over the full stacktrace, which can be extremely verbose. If you really need the full stacktrace, use -S or --full-stacktrace.

To log messages to standard output from the build file, the simplest way is to write to standard output:

println 'A message logged at the default level'

Anything written to standard output is automatically logged at the QUIET level.

Gradle adds a property called logger to the build file, which is an implementation of an SLF4J logger. It has methods to log messages at any desired level.

println 'Quiet message (default)'
logger.quiet('Quiet message')
logger.error('Error message')
logger.warn('Warning message')
logger.lifecycle('Lifecycle message')
logger.info('Info message')
logger.debug('Debug message')
logger.trace('Trace message')

task myTask {
    doLast {
        logger.info 'Info message inside myTask'
    }
}

You can use an explicit SLF4J logger from other classes (such as those in plugins) but creating a logger yourself.

import org.slf4j.Logger
import org.slf4j.LoggerFactory

Logger myLogger = LoggerFactory.getLogger('my-logger')
myLogger.info('An info message using slf4j')

Specifying Build Properties

Gradle offers multiple ways to specify properties for your build. In addition to the gradle.properties file discussed in The Gradle Daemon and Other Properties, you can also set properties as system variables or on the command line. This can be particularly useful when properties like usernames or passwords are required for publishing.

For example, consider the following extract from a Gradle build file in the User Guide on accessing password protected Maven repositories:

repositories {
    maven {
        credentials {
            username 'user'
            password 'password'
        }
        url "http://repo.mycompany.com/maven2"
    }
}

You probably don’t want to add hard-wired values for the username and password to a build file the way this one does. This section describes how to externalize their values.

Project and Task Properties

The build script itself is an instance of the Project class in the Gradle API. Any property with a getter and/or setter is a project property. For example, both Project and Task have a name property (see the getName() method in the Project API https://docs.gradle.org/current/javadoc/org/gradle/api/Project.html) or Task API.

println "Project name: $name" // Project name; configuration phase

task printProperties {
    println "Task name: $name"  // Task name; configuration phase
    doLast {
        println project.name
        println name
    }
}

Outside the task, name refers to the project name. Inside the task, name refers to the task name. The prefix project refers to the Project instance, so project.name invokes the getName() method.

Local Variables

You can also declare variables that are local to the build file. Local variables are declared with the def keyword from Groovy, and are only visible in the scope where they are declared.

def title = 'Local title'

task printProperties {
    doLast {
        println title
    }
}

Running gradle printProperties prints the value Local title, using the underlying Groovy system.

Extra Properties

To give properties more scope, Gradle model objects can also define extra properties using the ext keyword. This can be used in the normal fashion, either using a dot notation or a block if you want to set multiple properties.

ext.title = 'Local title'

task printProperties {
    doLast {
        println title
        println project.hasProperty('title')
    }
}

The title variable is available throughout the project, and in subprojects.

Setting Properties

Properties can be set in the gradle.properties file.

title='My title'

All properties in gradle.properties will automatically be available in the build.

task printProperties {
    doLast {
        println title
    }
}

You can use the -D flag to assign a system property using the underlying Java environment. You need to prefix the property with org.gradle.project to do so.

> gradle -Dorg.gradle.project.title=my_title printProperties

Finally, you can set a property on the command line using the -P flag.

> gradle -Ptitle=my_title printProperties

The command line approach has the highest priority.

subprojects {

    apply plugin: 'eclipse-wtp'

    repositories {

        manifest.attributes provider: 'gradle'

}

All the values in the subprojects block will be used by the descendent projects, so they don’t need to be repeated in their own build files. For example, the shared project under root doesn’t have a build file at all, because all the values it needs are already in the subprojects block in the root.

The services:shared subproject build is interesting.

dependencies {
    compile project(':shared')
}

The implication is that to build the services:shared project, Gradle must first build the shared project from the root. This can be seen in the build execution list above. This way you can configure one subproject to be dependent upon another.

The services:webservice subproject adds additional detail.

apply plugin: 'war'

version = '2.5'

dependencies {
    compile project(':shared'), 'commons-collections:commons-collections:3.2@jar', 'commons-io:commons-io:1.2', 'commons-lang:commons-lang:2.4@jar'
    compile project(path: ':api', configuration: 'spi')
    runtime project(':api')
}

This project is dependent upon the top-level shared and the api project, as well as having its own dependencies. You can even add additional plugins and project properties to it.

Executing a multi-project build

As shown in the previous section, you can invoke a task at the top level and it will run all the corresponding tasks in the children.

> gradle build
// runs all the build tasks in all the subprojects

You can also change directory to a particular subproject and run a task there.

> cd services/webservice
> gradle build
// runs `build` only on this subproject

Alternatively, you can give a fully-qualified task command from the root.

> gradle :services:webservice:build
// builds the services/webservice project

That’s basically all there is to it. The only difference between subprojects and allprojects is that the latter is used if the top-level project is also a project.

Gradle Plugins

Gradle is a plugin based architecture. The distribution includes a small number of useful plugins, but many more are available from the community.

There are two types of plugins:

  • Script plugins are other Gradle build files included in the current one

  • Binary plugins are classes that implement the Plugin interface

Plugins can reside inside the project, in a build script, or externally in a jar file.

Plugins are applied to a project. If a plugin has already been applied, doing so again has no effect.

Script Plugins

Script plugins are separate build files that are included in the current build using the from flag on the apply command.

apply from: 'other.gradle'

Note the typical use of Groovy’s optional parentheses. This command invokes the Project.apply() method.

Script plugins can be on the local file system or remote. Filesystem locations are relative to the project directory, while remote locations are specified using a URL.

For example, the Spock testing framework includes a sample project on Github (https://github.com/spockframework/spock-example). The build.gradle file includes the following line:

// ... lots of code ...

apply from: "gradle/ide.gradle"

// ... lots more code ...

The developers added a small Gradle script called ide.gradle inside the gradle folder. This line adds that script to the overall build.

Script plugins are just the Gradle include mechanism. The included file can be local (paths are resolved relative to the applying project) or remote, as via http. Imports are done at run time, so any changes to the included files are applied immediately. The included scripts are therefore not cached, so if they are not found, the build fails.

Binary Plugins

Binary plugins are added using the plugin syntax:

apply plugin: 'java'

Plugins are added using their plugin id. Core plugins (like the Java plugin) have a short name that can be used as shown. Community plugins use a fully qualified syntax.

Standard Gradle Plugins

Gradle comes with a relatively small number of plugins that can be applied right away. Among them are:

java, groovy, scala, antlr

Incubating languages

assembler, c, cpp, objective-c, objective-cpp, window-resources

Integration

application, ear, jetty, maven, osgi, war

Software development

announce, checkstyle, codenarc, findbugs, jdepend, project-report, signing, sonar

Several others are available. See the complete list in the User Guide at https://docs.gradle.org/current/userguide/standard_plugins.html.

Third-Party Portal

Many community plugins are listed at the portal web page, https://plugins.gradle.org/. Unfortunately, they aren’t arranged in any particular ordering, though there is a search box if you already know what you want.

Adding a plugin is a simple process that involves the Gradle syntax in the build file. You don’t need to manually download and install anything. There are two primary alternatives:

  • The buildscript block

  • The plugins block

One of the best of the community plugins is Gretty (for Gradle Jetty), which allows you to deploy and test a web application on Jetty or Tomcat as part of your build. The plugin page on the portal is https://plugins.gradle.org/plugin/org.akhikhl.gretty. It has a link to the Github page for the source code, https://github.com/akhikhl/gretty, which also contains all the documentation.

One way to add the plugin to your build is to use a buildscript block:

Example 37. Adding the gretty plugin using buildscript
buildscript {
  repositories {
    maven {
      url "https://plugins.gradle.org/m2/"
    }
  }
  dependencies {
    classpath "org.akhikhl.gretty:gretty:1.2.4"
  }
}

apply plugin: "org.akhikhl.gretty"

The buildscript block tells Gradle to access the plugin with the given coordinates at the specified repository, download it, and add it to the build. The plugin is then made available inside the build using the apply plugin: 'org.akhikhl.gretty' syntax as shown.

The buildscript syntax is very common, and is an easy way to download the appropriate jar files and make them available in your build.

There is a simplified syntax that is currently considered incubating, but looks quite promising. Instead of the buildscript block shown above, use a plugins block instead:

Example 38. Adding gretty using the plugins block
plugins {
  id "org.akhikhl.gretty" version "1.2.4"
}

This uses the full syntax of plugin name, id, version, and number. Both the id and the version number must be constant, literal strings.

A similar syntax can be used for the core plugins:

Example 39. Adding the core Java plugin
plugins {
    id 'java'
}

No further configuration is necessary.

Creating Your Own Plugin

Binary plugins are classes that implement the Plugin interface. The interface specifies a generic type, which is almost always Project, as the following sample from the User Guide shows.

class MyPlugin implements Plugin<Project> {
    void apply(Project project) {
        Task myTask = project.tasks.create('myTask')
        myTask.doLast {
            println 'added by a binary plugin'
        }
    }
}

The single method in the interface is apply, as shown in the example. The argument to the method is a reference of type Project, which you can use to manipulate the directed acyclic graph of tasks. Here, the code adds a task called myTask, which simply prints that it was added by a binary plugin.

The new plugin is applied as usual:

apply plugin: com.mycompany.plugins.MyPlugin

or you can use just the plugin ID:

apply plugin: 'com.mycompany.my-plugin'

where the id is defined in a properties file. The name of the file is the id (here com.mycompany.my-plugin), followed by .properties, and it must be stored in the META-INF/gradle-plugins directory. The contents of that file is the single line:

implementation-class=com.mycompany.plugins.MyPlugin

that specifies the implementation class.

Using a script plugin

Script plugins are regular tasks defined in their own Gradle build file. Using them is done via the apply from: command, which is a simple import.

  1. Define a script called script.gradle with the following contents:

    task fromPlugin() {
    doLast {
        println 'added from script.plugin'
    }
}

  2. Inside build.gradle, add an apply command that uses the script plugin.

    apply from: 'script.gradle'

  3. Run the gradle tasks command to see the imported task.

  4. Execute the imported task

Creating a Plugin

  1. Add a task to your build file called getJoke that retrieves a joke from ICNDB:

    Example 40. Retrieving a joke from ICNDB
    task getJoke {
    doLast {
        String base = 'http://api.icndb.com/jokes/random?'
        String qs = [firstName: 'Hans', lastName: 'Dockter',
                     limitTo  : '[nerdy]'].collect { it }.join('&')
        String jsonTxt = "$base$qs".toURL().text
        def json = new groovy.json.JsonSlurper().parseText(jsonTxt)
        String joke = json.value.joke
        println joke
    }
}

  2. Test out your new task by executing gradle getJoke and verify that a joke is returned. The "hero" ought to be Hans Dockter, the head of the Gradle project

  3. Make the build task depend on the getJoke task

    build.dependsOn 'getJoke'

  4. Run the build task and see that the build finishes with a joke

  5. Create a new Gradle build file called joke.gradle and move the getJoke task into that file. (Feel free to replace the qualified JsonSlurper reference with an import now)

  6. Apply the new script plugin by adding the following to the top of your build file

    apply from: 'joke.gradle'

  7. This time, create a custom task for the joke:

    1. Create a folder called buildSrc in the root directory. This is a predefined directory by Gradle that automatically supports src/main/groovy, src/main/java, src/main/kotlin, and src/main/resources subdirectories.

    2. In the buildSrc/src/main/groovy directory, add a class called JokeTask that contains a @TaskAction that gets the joke:

      import groovy.json.JsonSlurper
import org.gradle.api.DefaultTask
import org.gradle.api.tasks.TaskAction

class JokeTask extends DefaultTask {
    String firstName = 'Luke'
    String lastName = 'Daley'

    @TaskAction
    void getJoke() {
        String base = 'http://api.icndb.com/jokes/random?'
        String qs = [firstName: firstName, lastName: lastName,
                     limitTo  : '[nerdy]'].collect { it }.join('&')
        String jsonTxt = "$base$qs".toURL().text
        def json = new JsonSlurper().parseText(jsonTxt)
        println json.value.joke
    }
}

    3. In the root build.gradle file, create two tasks of type JokeTask:

      task getJoke(type: JokeTask)

task getJokeWithName(type: JokeTask) {
    firstName 'Cédric'
    lastName 'Champeau'
}

  8. Running gradle getJoke and gradle getJokeWithName will now produce a joke using either Luke Daley or Cédric Champeau, respectively.

  9. Now to turn this system into a plugin. In the buildSrc/src/main/groovy folder, create a class called JokePlugin that implements the Plugin<Project> interface

    import org.gradle.api.Plugin
import org.gradle.api.Project

class JokePlugin implements Plugin<Project> {
    @Override
    void apply(Project project) {
        project.task('getJoke', type: JokeTask)
    }
}

  10. In the build.gradle file, comment out our existing getJoke and getJokeWithName tasks. Instead, import the new plugin:

    apply plugin: JokePlugin // NOTE: do NOT put quotes around JokePlugin

  11. Now if you run gradle tasks, there should be a getJoke task anyway, even though we removed the ones we wrote explicitly. Invoking the getJoke task should work as before.

  12. To add input data from the build file, we need an extension. Add a class called JokePluginExtension to the buildSrc/src/main/groovy directory.

    class JokePluginExtension {
    String firstName = 'Hans'
    String lastName = 'Dockter'
}

    Initializing the two properties in the extension means setting the corresponding values in the Gradle build file is optional.

  13. The plugin needs to register the extension in order to use it. You register the extension by adding the following line at the beginning of the apply method

    void apply(Project project) {
    project.extensions.create('user', JokePluginExtension)
    // ...
}

  14. Inside the build.gradle file, you can now add a user block that sets the firstName and lastName properties

    user {
    firstName 'Paul'
    lastName 'King'
}

  15. It’s easy enough to get these values into the plugin. Inside the plugin class they are referred to as project.user.firstName and project.user.lastName. The tricky part is passing them along to the JokeTask, which has to be done after the properties are set. The trick is to use a property of all DefaultTask classes called conventionMapping, which you can set inside the apply method:

    void apply(Project project) {
    project.extensions.create('user', JokePluginExtension)
    project.task('getJoke', type: JokeTask)
}

    This will use the default values for firstName and lastName in the JokeTask

  16. To pass the values in the user extension to the custom task, change the JokeTask to refer to them explicitly:

    @TaskAction
void getJoke() {
    String base = 'http://api.icndb.com/jokes/random?'
    String qs = [firstName: project.user.firstName,
                 lastName : project.user.lastName,
                 limitTo  : '[nerdy]'].collect { it }.join('&')
    String jsonTxt = "$base$qs".toURL().text
    def json = new JsonSlurper().parseText(jsonTxt)
    println json.value.joke
}

  17. Now you can run the getJoke task from the build and the name of the hero will be set to the values in the user block in build.gradle

  18. This works, but restricts the plugin to only the current build project. As an alternative, you could make a completely separate project just for the plugin. The Gradle build file for that project would be:

    apply plugin: 'groovy'

dependencies {
    compile gradleApi()
    compile localGroovy()
}

    This build is implicitly what is being used inside the buildSrc folder.

  19. Then you would need to add a properties file to the src/main/resources/META-INF/gradle-plugins folder. The name of the properties file is the id of the plugin, which you can choose however you like. One idea might be com.kousenit.joke.properties. The contents of that file would be a single line:

    implementation-class=JokePlugin

    The value is the fully-qualified package name of the plugin class, which here is assumed to be in the default package.

  20. Once all that is done, then you need to publish your plugin in a way that you can then find it in the original build. The relevant chapters in the User Guide ("Publishing Ivy" and "Publishing Maven") contain the details.

IDE Integration

Gradle supplies two plugins that make it easy to work with Integrated Development Environments: the eclipse plugin and the idea plugin. Each helps to customize a project, generating the proper IDE-specific files and folders.

Eclipse

The eclipse plugin is added in the usual manner.

apply plugin: 'java'
apply plugin: 'eclipse'

// ... rest of the Java project tasks ...

There are two separate Eclipse plugins available. The eclipse plugin is for regular projects, and the eclipse-wtp (web tools project) is for web applications.

eclipse

For Java projects, generates a .project file and .settings folder with the correct configuration. Adds the additional required settings for Groovy projects.

eclipse-wtp

In addition to the above, also generates the settings to define a Dynamic Web Project in Eclipse. Includes the eclipse plugin automatically.

While each adds several tasks to the build, by far the most commonly used are eclipse and cleanEclipse. The former generates the files and folders necessary to define an Eclipse project, where any required dependencies are linked to the local repository. The latter removes any Eclipse settings.

It’s easiest to use them together.

> gradle cleanEclipse eclipse

This will remove any existing project and settings files and re-generate them. It can be run repeatedly whenever the dependencies change. The resulting project can be imported into Eclipse as an existing project (File -→ Import…​ -→ Existing Projects into Workspace).

Note if you want to guarantee both tasks occur in the proper order, add a task dependency to the build file.

tasks.eclipse.dependsOn cleanEclipse

Running the eclipse task will then automatically execute cleanEclipse first.

The eclipse-wtp project uses the same tasks to build a dynamic web project.

Source Sets

The eclipse plugin makes it easy to convert a Gradle project into an Eclipse project. If you create a Java project inside Eclipse, however, it will not have the expected source code layout (Java sources in src/main/java and tests in src/test/java). This can be configured using the sourceSets block.

As source set is, naturally enough, a set of source files. The sourceSets block has a number of interesting properties (see the User Guide for details), one of which is name. The Java plugin defines two source sets.

apply plugin: 'java'

sourceSets.all {
    println name
}

// ... normal repositories and dependencies ...

Executing a build gives the following.

> gradle build
main
test
:compileJava
// ... other Java tasks ...

To map the expected source folders to your existing one, use those names. In a normal Eclipse project, for example, the source code goes into a directory called src and there is no separate source folder for tests. Say we create one called test. The resulting build file needs to be:

apply plugin: 'java'
apply plugin: 'eclipse'

sourceSets {
    main {
        java {
            srcDir 'src'
        }
    }
    test {
        java {
            srcDir 'test'
        }
    }
}

repositories {
    jcenter()
}

dependencies {
    testCompile 'junit:junit:4.12'
}

Adding this Gradle build file to an existing Eclipse Java project will build it correctly, and if you also run gradle cleanEclipse eclipse Gradle will add the JUnit dependency as a Referenced Library from the local repository.

Buildship

Recent versions of Eclipse have included a new Gradle plugin called Buildship. NOTE: Buildship is a Gradle plugin for Eclipse, as opposed to the Eclipse plugin for Gradle that is applied to a build.

Buildship is supposed to make it easy to create projects or import them, and give a task view with capabilities similar to IntelliJ IDEA. See http://gradle.org/eclipse/ for details.

The plugin may in fact work just fine. This author’s personal experience, however, is that exiting to the shell and running gradle cleanEclipse eclipse and refreshing the project in the IDE hasn’t failed in years. Feel free to experiment with Buildship, but keep that in mind as a fallback position.

IntelliJ IDEA

In most cases, the idea plugin isn’t necessary. When importing an existing Gradle project, navigate to the build.gradle file during the import process and the IDE takes care of the rest.

IntelliJ includes a Gradle view that sorts the tasks into groups and can be used to execute them. If you customize the Gradle build or add your own tasks, IDEA may not automatically update the result. The fix is to click the "Synchronize" button, or the "Refresh all Gradle projects" button in the upper left corner of the Gradle window, which should rebuild the project correctly.

The idea plugin does include a cleanIdea task, which reinitializes a project that has somehow stopped working. Running gradle cleanIdea idea from the command line is as useful as the Eclipse version, though most of the time you won’t need it.
